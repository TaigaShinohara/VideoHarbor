## 実装の順序と完了条件

### 1. 文書・連絡先・今後のGit識別情報

内部リンク、個人アカウント固定URL、連絡先案内を整理し、repo内のGit識別情報を設定する。公開用の文書と内部の作業記録を混同しない。

完了条件: 追跡ファイルの内部Notion URL・元ページID・不要な所有者固定URLが除かれ、出典を失わず読めること。指定メール以外の新しい私的連絡先がなく、次のコミットのauthor/committerとマージ後のmetadataが期待した分類であること。既存履歴に残る情報は別に報告する。

### 2. URLの表示を安全にする

`workspace-videos.js` と共通表示処理で、表示する情報と取得用の完全URLを分ける。query名の拒否リストによる部分的伏字は、未知のキーやpath内の署名を見逃すため採用しない。通常の詳細へ生URLを出す操作やコピー機能は追加しない。`fileLabel()`から来るURL basenameや、`data-url`属性も対象にし、DOM上の操作対応には候補IDを使う。元URLはメモリ上の候補から引く。

新しい設定や確認ダイアログは設けず、動画の題名・プレビュー・候補番号・形式・元ページ確認で選べる状態を保つ。host自体が個人のサービス名等を含む可能性は残るが、必要な配信元許可を隠さない。

完了条件: 未知の認証query、path内のopaque値、大小文字・長いURL・blobの合成入力を使い、text/tooltip/aria/通常エラー/DOM属性に値が出ないこと。録画選択欄の `option.value` 内のJSON（documentURLを含む）も候補ID化の対象とする。query違いの候補を混同せず、直接/HLS/DASH/blob保存が元の完全URLで成功すること。keyboard・狭幅・候補選択も確認する。

### 3. 閉鎖後のsessionを最小化する

`background.js` の通常閉鎖と、次回起動時に閉鎖済みと判明した経路を共通化する。既存の直列queue内で、候補一覧・過去候補・動画参照・JPEG・frame・元ページURL/題名・通知を除去する。

待機中jobは完全URL・確定済みファイル名・形式を保持する。Chrome受付済みjobはdownload ID・状態・必要な形式判定を中心にし、不要なURL・pathを保持しない。`refreshJob()`が取得する絶対pathを閉鎖sessionへ書き戻さないよう、読込み・保存の両方を確認する。全jobが終端になればsessionを除去する。

完了条件: 閉じた直後に不要な情報がなく、複数job・閉鎖とdownload完了の競合・画面移動・Worker再起動・中断でも保存が継続し、終端でsessionが消えること。開いている作業タブの再試行と結果確認を壊さないこと。

### 4. 新規保存名を統一する

`utils.js` の直接保存名、`media-save.js` の組立保存名、`recorder.js` の録画名とpicker候補名を共通方針にそろえる。例は `VideoHarbor/2026-11-01/video-190000-001.mp4`。日付・連番は例であり、再試行中は確定済みの名前を保つ。

まずは中立名を既定にし、題名使用の新しい設定は追加しない。検証で探しにくさが認められた場合に限り、既存の詳細内に任意の題名利用を置く案を再評価する。画面には実際の保存名と保存場所への導線を残す。

完了条件: 題名やURL basenameに個人情報風の合成値があっても既定名へ入らず、拡張子と実形式が一致すること。同名の連続保存・retry・MP4/元形式・録画・順次保存・picker改名が正しく、既存ファイルや履歴に手を加えないこと。

### 5. 再混入を検出し、全体を再監査する

開発用のローカル情報検査を再実行できる形にする。製品の実行時依存や外部送信を増やさない。実資格情報形式、内部文書URL、個人home path、指定外の連絡先等を値を出さず検出する。合成fixture・公開の出典・第三者表記の例外はファイル/用途を限定し、テスト全体を無条件除外しない。今回はクラウドCIや有料スキャンを自動起動する計画にしない。

完了条件: 追跡ファイル・製品同梱物・取得済みGit履歴を再走査し、残る識別情報と除去した現行情報を区別できること。`npm test` / `npm run check`、差分確認、隔離Chromeの保存・録画・再起動・通信・中断の関連試験を通す。実OS picker・実音声・人間の体験は別途確認し、自動PASSで代替しない。

## 過去履歴と公開の扱い

推奨は、現在の非公開開発履歴を保持し、将来の公開時に監査済みsnapshotから過去の内部情報を含めない公開履歴を作る案を比較すること。今回、実資格情報も通常の個人メールも発見していないため、履歴書換えやforce pushを必須にはしない。Gitの作者名や所有者との関連を隠す必要があるなら、公開先・所有者の選択も必要になる。

既存履歴の書換えを選ぶ場合は、対象ref・全clone/worktree・置換対象・第三者作者の保持・保全先・旧ref・GitHub側の残存・復旧手順を具体化する。commit ID変更、PR差分への影響、旧cloneからの再混入を評価してから実行判断する。`.mailmap`等の表示変更だけで元objectの除去とは扱わない。公開、force push、ref削除は通常のPRとは別の実行段階であり、この計画の保存では実行しない。[GitHub公式の履歴除去と副作用](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)

## 進め方と復旧

工程1、2、3、4、5の順に、小さなPRへ分けて検証・マージする。今回の計画・監査訂正PRは実装工程の完了に数えない。各実装PRの開始時に最新コードとdirty workを再確認する。

不具合が出た場合は該当PR単位で復旧し、他の工程の保護を維持する。URL表示の復旧で生URLの常設表示へ戻す、閉鎖処理の失敗を保存済みデータの削除で解消する、といった復旧は採用しない。進行中の録画・未保存データを保護し、必要なら新機能を止めたまま修正する。
